## チーム結成の出発点

これまで私はさまざまなゲームプロジェクトを企画・開発してきたが、そのほとんどは一人で進める個人プロジェクトであった。

（これまで企画・開発してきたゲームプロジェクト、投稿日現在）<br>
（廃棄・中断したプロジェクトを含む）

|                     Project                     |         Period        | Project Type |          Genre         |     Result     |
| :---------------------------------------------: | :-------------------: | :----------: | :--------------------: | :------------: |
|                    Project S                    | 2020. 10. ~ 2021. 12. | Solo Project |      Hero Shooter      | ⏸️ Interrupted |
| Astral Days! <br> (Project AD) <br> (Project A) | 2020. 10. ~ (Ongoing) | Solo Project | Story-based Action RPG |   🔄 In Progress   |
|                    Project R                    |  2020. 12. ~ 2021. 1. | Solo Project |           RPG          | ⏸️ Interrupted |
|                    Project F                    |  2020. 12. ~ 2022. 1. | Solo Project |       Action RPG       | ⏸️ Interrupted |
|               Python Game Contest               | 2023. 06. ~ 2023. 07. | Team Project |   2.5D Rhythm Action   | ⏸️ Interrupted |

上の表からも分かる通り、これまで進めてきた、あるいは現在進行中のプロジェクトの中で、チームプロジェクトはたった一つしかなかった。それすら最後まで完成させることができず、中断してしまった。

そんな中、大学に入学した私はゲーム開発中央サークルGAMMARUに合格し、最初は**準会員**として入部することになった。<br>
（GAMMARUでは、入部時は**準会員**として始まり、その後コンテストに参加することで**正会員**へ昇格できる。もし一学年以内に昇格できなかった場合は、自動的に退部扱いとなる。）

私はGAMMARUに入部してからさまざまな活動に参加してきたし、これからも活動を続けていきたいと考えていた。そのため、私にとって正会員へ昇格する機会であるコンテストへの参加は、ほとんど必須に近いものだった。

正会員昇格のためのコンテストは年に二回行われる。新入部員のみが参加できる**夏コンテスト**と、全部員が参加できる**冬コンテスト**である。

しかし、個人的な学業計画として冬にはJLPT資格の取得と大学の冬季学期の準備をしなければならなかったため、冬コンテストまで並行して参加するのは難しいと判断した。
こうして私は夏コンテストに参加することを決めた。

基本的にGAMMARUのコンテストには、チームの人数制限が存在しない。つまり、一人で参加することも可能なのである。

しかし今回だけは、一人でコンテストに参加するのではなく、チームを組んで一つのプロジェクトを一緒に作ってみたいと思っていた。

これまでほとんどすべてのプロジェクトを一人で進めてきたし、過去に一度チームプロジェクトへ参加した経験はあったものの、そのプロジェクトも最後まで完成させることはできなかった。そのため、複数人で役割を分担し、一つのゲームを最後まで作り上げていく本格的なチーム開発は、事実上初めてと言ってもよかった。
それだけでなく、この機会を通してGitなどを活用した実際の共同開発を経験し、複数人で一つの目標を共有しながらプロジェクトを最後まで完成させてみたいとも考えていた。

そこで複数のチームの募集投稿を確認した後、その中で最も魅力的に感じた**「ERROR CODE: H」**プロジェクトに参加することを決めた。

## 小さな問題の連続

### 役割分担の問題

チームを結成した後、最初に直面した問題は役割分担であった。

今回のプロジェクトのメンバーは全員、ゲーム開発に関するチームプロジェクトをきちんと最後まで完成させた経験がなく、さらに4人全員の得意分野がプログラミングであった。
実のところ、これはある程度自然なことでもあった。

GAMMARUは現在、ゲーム開発の**中央**サークルであるが、もともとはソフトウェア学部所属の**小規模サークル**として始まったからである。

こうした背景もあってか、現在でもプログラミングを主分野とするメンバーの割合が最も高く、その反対にアートやサウンド分野の人数は比較的少ない。

私たちのチームも、この問題の例外ではなかった。

プログラミングができるメンバーは4人全員だったが、企画ができるメンバーは2人、アートとサウンドはそれぞれ0人と1人に過ぎなかった。
結局、誰かが自分の得意分野ではない役割まで担当しなければならなかった。

何度かのオンライン・オフライン会議を重ねた結果、私を含む3人がプログラミングを担当し、そのうち私ともう1人がアートも兼任することになった。企画とサウンドはそれぞれ1人ずつ担当する形で、最終的な役割を決めた。
こうして互いに足りない分野を兼任する形で、役割分担の問題はひとまず解決することができた。

しかし、役割を決めることと、その役割を実際にきちんとこなせることは、まったく別の問題であった。

### 経験値不足

メンバー全員の得意分野がプログラミングだったこともあり、プログラミングそのものには大きな問題はなかった。
特に、ゲームプロジェクトではないものの、別のプログラミング関連のチームプロジェクトを経験した先輩がいたため、Gitなどを活用した共同開発の手順や基本的なルールも比較的早い段階で整理することができた。

問題は、それ以外の分野であった。

一つ目は企画である。

「ERROR CODE: H」の企画は、チームリーダーを担当した先輩が以前から準備していた企画案をベースに進められた。

ただし、一つの企画案が存在することと、実際の開発過程でその企画を作業単位に分けることは別の問題であった。

どの作業を最初に進めるべきなのか、それぞれの作業をどの程度の大きさに分けるべきなのか、そしてそれを誰にどのように割り振るのか、その基準から新たに決めなければならなかった。

初期段階ではこうした基準が十分に定まっていなかったため、作業の優先順位や分担方法を決めるだけでも予想以上に時間が必要となった。
当然ながら、プロジェクト初期の進行速度も多少遅くならざるを得なかった。

サウンドにも似たような問題があった。

最近ではAIなどのツールによって簡単なゲームサウンドを制作しやすくなったが、メンバーの中には本格的なサウンド制作を経験した人がいなかった。
簡単なゲームBGMであればAIを活用してある程度対応できたものの、それ以外のSFXまでしっかり制作するのは簡単ではなかった。

その結果、サウンドもまた、プロジェクトを進めながら継続して解決していかなければならない課題として残ることになった。

しかし、本当の問題は別にあった。

<br>

それが、アート分野であった。

チーム内には、本格的なアート制作を経験した人が一人もいなかった。

私自身も、簡単な絵を描いたり、3Dモデリングを少し触ったりした程度の経験しかなかった。
しかし「ERROR CODE: H」は、**2Dドット絵スタイル**のゲームであった。

一言で言えば、私を含むアート担当者たちは何も分からないまま、アートという深海へそのまま投げ込まれたようなものだった。
それどころか私は、2Dドット制作に使うアートツールすら持っておらず、自費で新しく購入しなければならなかった。

問題は、ツールを一つ用意すれば終わるようなものでもなかった。

`Pixel Perfect`をどのように適用するのか、全体的な`解像度`をどう設定するのか、さらにキャラクターやオブジェクトの`ドットサイズ`をどの程度に統一するのかなど、初めて直面する問題が波のように押し寄せてきた。

それでも私は、アート担当として任された役割を果たさなければならなかった。

理由は単純である。自分が引き受けると決めた役割だったからだ。

最終的には、アート制作を一緒に進めていく中で、自然と役割を再調整することになった。

私よりもドットアニメーション制作に慣れていった別のメンバーがキャラクターのドットアニメーションを担当し、私はUIをはじめとする各種デザイン作業を担当する形である。
最初に決めた役割分担がそのまま維持されたわけではなかったが、それぞれが少しでも得意な分野を見つけながら、役割を調整していった。

### それぞれのスケジュールの衝突

いくら長期休暇中に進めるプロジェクトとはいえ、全員が休暇のすべてをプロジェクトだけに使えるわけではなかった。

資格試験の準備をしなければならない人もいれば、アルバイトの予定によって特定の時間帯には会議への参加が難しい人もいた。
そのほかにも旅行の予定や家族の看病など、それぞれにさまざまな事情があった。

そのため、4人全員が参加できる会議の時間を決めることさえ、想像していたより簡単ではなかった。
ただし、スケジュールの問題についてはチームメンバー全員が理解している部分でもあった。

そこで、基本的な会議は毎週日曜日に行い、やむを得ず予定を変更する必要がある場合には事前に共有し、互いのスケジュールを調整する形で進めることにした。

## プロジェクトの始まり

プロジェクトが始まる前からさまざまな問題が続けて発生したものの、私たちはついにスタートラインに立った。

複数人がそれぞれの役割を分担し、一つのゲームを最後まで完成させることを目標に本格的なチーム開発を進めるのは、私たち全員にとって事実上初めてと言ってもよかった。
だからこそ、これからもきっと数え切れないほどの試行錯誤が待っているだろう。
実際、プロジェクトを始めるための準備段階ですら、予想していなかった問題が次々と現れたのだから。

しかし、それぞれが得意な部分を最大限に活かし、互いに足りない部分を補っていけば、少なくとも今回こそは一つのプロジェクトを最後まで完成させることができると思っている。

最初から完璧なチームである必要はない。
互いの足りない部分を一つずつ補いながら、最後まで作り上げればいい。

こうして2026年7月5日、私たちにとって初めての本格的なゲーム開発チームプロジェクトである「ERROR CODE: H」が始まった。

**Project「ERROR CODE: H」、ここに始動！**
