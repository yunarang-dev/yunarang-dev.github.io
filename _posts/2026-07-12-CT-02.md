# [ERROR-CODE-H 개발일지] 1주차 — 전투 정보를 한눈에 보여주는 Heat·Core UI 만들기

**개발 기간:** 2026.07.05 ~ 2026.07.13
**담당 역할:** 인게임 HUD 기획 및 Heat·현재 Core 표시 기능 구현

공모전 팀 프로젝트 **『ERROR-CODE-H』**의 개발이 시작되었다.

우리 팀은 매주 회의를 통해 그 주에 필요한 기능을 정하고, 각자의 역할을 나누어 개발을 진행하기로 했다. 1주차에는 플레이어 조작, 적의 피격 및 공격 판정, Core 전환, Heat 시스템 등 게임의 기본적인 전투 구조를 만드는 작업이 동시에 진행되었다.

나는 그중 플레이어가 전투 상황을 빠르게 파악할 수 있도록 **인게임 UI를 기획하고, 현재 Heat와 장착 중인 Core를 표시하는 기능**을 맡았다.

이번 주의 목표는 단순히 화면 위에 게이지를 배치하는 것이 아니었다. 팀원이 구현한 Heat와 Core 시스템에서 상태가 변경되었을 때, 그 결과가 실제 HUD에 자연스럽게 반영되도록 연결하고, 이후 다른 전투 정보도 추가할 수 있는 UI의 기본 구조를 만드는 것이었다.

## 인게임 UI 기획안 제작

가장 먼저 전투 중 플레이어가 어떤 정보를 확인해야 하는지 정리하고, 각 정보를 어느 위치에 배치할지 구상했다.

『ERROR-CODE-H』에서는 검·체인·총 Core를 전환하며 공격과 스킬을 연계한다. 공격하거나 Core를 교체하면 Heat가 증가하기 때문에, 플레이어는 전투 중에도 현재 장착 중인 Core와 누적된 Heat를 지속적으로 확인할 필요가 있었다.

이러한 게임의 특징을 바탕으로 UI 기획안에는 다음과 같은 요소를 배치했다.

* 현재 장착 중인 Core
* 교체 가능한 Core 목록
* 현재 Heat를 나타내는 원형 게이지
* 플레이어의 HP 바
* 공격 및 스킬 상태를 보여주는 하단 UI

**[이미지 1 삽입 — 1주차 인게임 UI 기획안]**

> 1주차에 제작한 인게임 UI 기획안. 전투 중 시선을 크게 분산시키지 않으면서 현재 Core와 Heat 상태를 확인할 수 있도록 좌측 상단에 핵심 정보를 모아 배치했다.

현재 장착 중인 Core는 좌측 상단에 크게 표시하고, 교체 가능한 Core는 그 아래에 작은 아이콘으로 배치하는 방향으로 구성했다. Heat 게이지와 HP 바 역시 같은 영역에 묶어, 플레이어가 화면 여러 곳으로 시선을 옮기지 않고도 주요 전투 정보를 한 번에 파악할 수 있도록 했다.

하단에는 기본 공격, 가드, 스킬 등 전투 행동을 보여주는 영역을 구상했다.

다만 이번 기획안은 최종 UI 디자인을 확정하기 위한 시안이라기보다, **게임에 필요한 정보의 우선순위와 각 요소의 배치 관계를 정리하기 위한 초기 설계안**에 가까웠다.

따라서 1주차의 실제 구현 범위는 기획안에 포함된 요소 가운데 **Heat와 현재 Core 표시 기능**에 집중했다.

## 별도의 UI 테스트 환경 만들기

처음부터 개발 중인 플레이어 씬에 UI를 직접 추가할 경우, 다른 시스템에서 발생한 문제와 UI 자체의 문제를 구분하기 어려울 수 있다고 판단했다.

그래서 먼저 `UITestScene`이라는 별도의 테스트 씬을 제작했다. 임시 이미지와 텍스트를 이용해 HUD를 구성하고, 실제 전투 시스템과 연결하기 전에 게이지의 기본적인 동작부터 독립적으로 확인할 수 있도록 했다.

초기 테스트 씬에는 다음과 같은 요소를 추가했다.

* Heat 게이지 프레임과 채움 이미지
* Heat 수치를 표시하는 텍스트
* 테스트용 HP 게이지
* 임시 Core 이미지
* 키 입력으로 수치를 변경하는 테스트 스크립트

테스트 단계에서는 `UITestManager`가 임시 Heat 값을 가지고 있고, 키를 누르면 해당 값이 증가하거나 감소하도록 만들었다.

```csharp
private float currentHeat = 0f;

private void Update()
{
    if (Input.GetKeyDown(KeyCode.E))
    {
        currentHeat = Mathf.Clamp(currentHeat + 10, 0, 100);
        _heatUI.SetHeat(currentHeat);
    }

    if (Input.GetKeyDown(KeyCode.R))
    {
        currentHeat = Mathf.Clamp(currentHeat - 10, 0, 100);
        _heatUI.SetHeat(currentHeat);
    }
}
```

`E` 키를 누르면 Heat가 10씩 증가하고, `R` 키를 누르면 10씩 감소한다. 변경된 값은 `SetHeat()`를 통해 곧바로 Heat UI에 전달된다.

물론 이 코드는 실제 게임의 Heat 시스템이 아니다. 팀원이 구현한 `HeatManager`와 연결하기 전에, **UI가 전달받은 값에 따라 정상적으로 변화하는지만 확인하기 위한 테스트 코드**였다.

실제 시스템과의 연동을 시작하기 전에 UI 자체의 문제를 먼저 분리해 검증하고자 한 것이다.

## Heat 값을 게이지와 퍼센트로 표시하기

Heat UI에서는 전달받은 수치를 그대로 사용하는 것이 아니라, Unity UI 이미지에서 사용할 수 있는 값으로 변환할 필요가 있었다.

Unity UI 이미지의 `fillAmount`는 `0`부터 `1` 사이의 값을 사용한다. 따라서 0부터 100까지의 Heat 값을 100으로 나누어 게이지의 채움 비율로 변환했다.

```csharp
public void SetHeat(float current)
{
    current = Mathf.Clamp(current, 0f, 100f);

    heatFill.fillAmount = current / 100f;

    if (heatText != null)
        heatText.text = $"{current:0}%";
}
```

먼저 `Mathf.Clamp()`를 사용해 Heat 값이 0보다 작아지거나 100을 초과하지 않도록 제한했다.

그다음 현재 Heat를 100으로 나눈 값을 `fillAmount`에 전달했다. 예를 들어 Heat가 50이라면 `fillAmount`에는 `0.5`가 들어가고, 게이지는 절반만 채워진다.

동시에 같은 값을 정수 형태의 퍼센트 텍스트로 표시했다.

* Heat 0 → 게이지 0%, 텍스트 `0%`
* Heat 50 → 게이지 50%, 텍스트 `50%`
* Heat 100 → 게이지 100%, 텍스트 `100%`

1주차 당시 Heat 시스템의 최대값이 100을 기준으로 만들어져 있었기 때문에, UI 역시 동일하게 100을 기준으로 계산하도록 구성했다.

구조 자체는 단순했지만, 이후 실제 Heat 시스템과 연결할 때도 같은 표시 로직을 그대로 사용할 수 있도록 먼저 분리해 둔 것이 중요했다.

## HP UI는 연결할 자리만 남겨두기

UI 기획안과 초기 테스트 씬에는 HP 바도 포함되어 있었다.

테스트 씬에서는 임시 HP 값을 증가시키거나 감소시키는 구조를 만들어 게이지의 표시 방식까지 시험했다. 그러나 7월 13일 당시에는 실제 HP 시스템이 UI와 연결할 수 있는 형태로 아직 준비되지 않은 상태였다.

따라서 이번 주에는 HP 연동까지 임의로 확장하지 않고, **향후 연결할 수 있는 자리만 남겨둔 채 Heat와 Core UI를 먼저 완성**하기로 했다.

당시 디스코드에도 다음과 같이 작업 결과를 공유했다.

> UI 통합 작업 완료했습니다. 아직 HP 관련된 부분은 없는 것 같아서 그 부분은 남겨두고 Heat, Core UI만 먼저 작업했습니다.

실제 `UIManager`에서도 HP UI 참조는 준비해 두었지만, HP 데이터를 관리하는 시스템은 아직 연결하지 않은 상태로 남겨두었다.

```csharp
[Header("UI Drawer References")]
[SerializeField] private HPDrawer _hpDrawer;
[SerializeField] private HeatDrawer _heatDrawer;
[SerializeField] private CoreDrawer _coreDrawer;

[Header("Variables References")]
//[SerializeField] private PlayerHealth _playerHealth;
[SerializeField] private HeatManager _heatManager;
[SerializeField] private CoreManager _coreManager;
```

`HPDrawer`가 들어갈 자리는 만들어두었지만, 실제 HP 데이터를 관리할 `PlayerHealth` 참조는 주석 처리되어 있다. 반면 이번 주의 구현 범위였던 `HeatManager`와 `CoreManager`는 실제 참조를 연결했다.

초기 상태를 표시하는 부분에서도 마찬가지였다.

```csharp
private void Start()
{
    //_hpUI.SetHP(currentHP, maxHP);
    _heatDrawer.SetHeat(_heatManager.CurrentHeat);
    _coreDrawer.SetCore(_coreManager.CurrentCoreData);
}
```

이 코드를 보면 당시의 작업 범위를 비교적 명확하게 확인할 수 있다.

* **HP UI:** 향후 연결을 위한 참조와 자리만 마련
* **Heat UI:** 실제 `HeatManager`의 현재 값과 연결
* **Core UI:** 실제 `CoreManager`의 현재 Core와 연결

아직 준비되지 않은 HP 시스템을 임시로 가정하여 구현하기보다, 현재 실제로 연결할 수 있는 Heat와 Core부터 먼저 통합하고 HP는 후속 작업으로 남겨두었다.

팀 프로젝트에서는 단순히 내가 맡은 기능만 빠르게 구현하는 것뿐 아니라, **다른 팀원의 작업 영역을 임의로 가정하지 않는 것** 역시 중요하다고 생각했다.

## 동일한 클래스 이름으로 발생한 충돌 해결

UI 테스트 기능을 팀 프로젝트에 합치는 과정에서는 예상하지 못한 클래스 이름 충돌도 발생했다.

팀원이 Core와 Heat 시스템을 구현하면서 이미 `HeatUI`라는 이름의 스크립트를 추가한 상태였는데, 내가 독립 테스트용으로 만든 스크립트 역시 같은 이름을 사용하고 있었다.

별도의 네임스페이스 없이 동일한 `HeatUI` 클래스가 두 개 존재하면 Unity 프로젝트에서 충돌이 발생할 수 있었다.

이를 해결하기 위해 테스트용 스크립트의 이름을 `HeatUITest`로 변경했다.

이후 실제 게임 시스템과 연결할 UI는 역할에 따라 다음과 같이 다시 나누어 구성했다.

* `HeatManager`: 실제 Heat 수치 관리
* `CoreManager`: 현재 장착 중인 Core 관리
* `HeatDrawer`: 전달받은 Heat 값을 게이지와 텍스트로 표시
* `CoreDrawer`: 현재 Core 정보를 UI에 표시
* `UIManager`: Heat·Core 시스템의 변화를 받아 각 UI로 전달

초기 테스트용 스크립트는 `TestScripts(Old)` 폴더로 옮겨 보관하고, 실제 게임에서 사용할 UI 표시 코드는 별도로 분리했다.

처음에는 단순한 이름 충돌 문제였지만, 이를 해결하는 과정에서 테스트 코드와 실제 통합 코드의 역할을 다시 나눌 수 있었다.

결과적으로 클래스 이름의 충돌을 해결하는 동시에, **각 스크립트가 무엇을 담당하는지 보다 명확하게 정리할 수 있었다.**

## Heat·Core 시스템과 UI 연결

팀원이 구현한 `HeatManager`와 `CoreManager`에는 각각의 상태가 변경될 때 알림을 보내는 이벤트가 존재했다.

* Heat가 변경되면 `OnHeatChanged` 이벤트 발생
* 현재 Core가 변경되면 `OnCoreChanged` 이벤트 발생

나는 `UIManager`가 이 두 이벤트를 구독하도록 구성했다.

```csharp
private void OnEnable()
{
    _heatManager.OnHeatChanged += HandleHeatChanged;
    _coreManager.OnCoreChanged += HandleCoreChanged;
}

private void OnDisable()
{
    _heatManager.OnHeatChanged -= HandleHeatChanged;
    _coreManager.OnCoreChanged -= HandleCoreChanged;
}
```

`OnEnable()`에서는 Heat와 Core의 변경 이벤트에 각각의 처리 함수를 등록했다.

반대로 `OnDisable()`에서는 앞서 등록한 이벤트를 해제했다. UI 오브젝트가 비활성화되거나 제거된 이후에도 이벤트가 남아 불필요한 호출이 발생하는 것을 방지하기 위해, 이벤트의 등록과 해제를 한 쌍으로 구성했다.

이 구조를 사용하면 UI 전체가 매 프레임 Heat와 Core의 상태를 확인할 필요가 없다.

실제 값이 변경되었을 때만 이벤트를 통해 필요한 UI를 갱신할 수 있고, 전투 시스템과 UI 사이의 역할 역시 보다 명확하게 나눌 수 있었다.

## Heat 변경 이벤트 처리

Heat 값이 변경되면 `HeatManager`는 현재 Heat와 최대 Heat를 함께 전달한다.

`UIManager`는 해당 이벤트를 받아 현재 Heat를 `HeatDrawer`에 넘기도록 했다.

```csharp
private void HandleHeatChanged(float currentHeat, float maxHeat)
{
    _heatDrawer.SetHeat(currentHeat);
}
```

이후 `HeatDrawer.SetHeat()`가 전달받은 값을 게이지의 채움 비율과 퍼센트 텍스트로 변환한다.

전체 흐름은 다음과 같다.

**플레이어의 공격 또는 Core 전환**
→ **`HeatManager`의 Heat 수치 변경**
→ **`OnHeatChanged` 이벤트 발생**
→ **`UIManager.HandleHeatChanged()` 호출**
→ **`HeatDrawer.SetHeat()` 호출**
→ **게이지와 퍼센트 텍스트 갱신**

씬이 처음 시작될 때에는 `HeatManager.CurrentHeat`를 직접 읽어 초기 UI를 표시하고, 이후부터는 Heat가 실제로 변경될 때마다 이벤트를 통해 UI가 갱신된다.

단순히 현재 값을 화면에 표시하는 것뿐 아니라, **Heat 값을 관리하는 영역과 이를 표현하는 영역을 분리했다는 점**이 이번 구조에서 중요한 부분이었다.

## 현재 Core 변경 이벤트 처리

현재 장착 중인 Core 역시 같은 방식으로 연결했다.

플레이어가 Core를 교체하면 `CoreManager`가 `OnCoreChanged` 이벤트를 발생시킨다. `UIManager`는 새로운 `CoreData`를 받아 `CoreDrawer`에 전달한다.

```csharp
private void HandleCoreChanged(CoreData coreData)
{
    _coreDrawer.SetCore(coreData);
}
```

`CoreDrawer`는 전달받은 `CoreData`에서 현재 Core의 이름을 읽어 화면에 표시한다.

```csharp
public void SetCore(CoreData coreData)
{
    coreText.text = coreData != null
        ? coreData.CoreName
        : "None";
}
```

정상적인 `CoreData`가 전달된 경우에는 현재 Core의 이름을 표시하고, Core가 지정되지 않은 경우에는 null 참조 오류가 발생하지 않도록 `None`을 표시했다.

전체 흐름은 다음과 같다.

**플레이어가 Core 교체**
→ **`CoreManager`의 현재 Core 변경**
→ **`OnCoreChanged` 이벤트 발생**
→ **`UIManager.HandleCoreChanged()` 호출**
→ **`CoreDrawer.SetCore()` 호출**
→ **현재 Core 텍스트 갱신**

초기 기획안에서는 현재 Core와 교체 가능한 Core들을 이미지 아이콘으로 표시하는 것을 목표로 했다.

하지만 1주차에서는 먼저 디자인을 완성하기보다, **실제 Core 변경 정보가 UI까지 정상적으로 전달되는 구조를 완성하는 것**에 집중했다.

아이콘이나 최종 디자인은 이후에도 얼마든지 변경할 수 있지만, 시스템에서 UI까지 데이터가 전달되는 구조는 이후 작업의 기반이 되기 때문이다.

## UI의 역할을 나누어 관리하기

통합 작업에서는 하나의 스크립트가 모든 UI 기능을 처리하지 않도록 역할을 분리했다.

`UIManager`는 게임 시스템과 UI 사이에서 데이터를 전달하고, `HeatDrawer`와 `CoreDrawer`는 전달받은 데이터를 실제 화면에 표시한다.

```csharp
public class UIManager : MonoBehaviour
{
    [Header("UI Drawer References")]
    [SerializeField] private HPDrawer _hpDrawer;
    [SerializeField] private HeatDrawer _heatDrawer;
    [SerializeField] private CoreDrawer _coreDrawer;

    [Header("Variables References")]
    [SerializeField] private HeatManager _heatManager;
    [SerializeField] private CoreManager _coreManager;
}
```

각 클래스의 역할은 다음과 같이 구분했다.

### `HeatManager`

* 현재 Heat 보관
* Heat 증가 및 감소 처리
* Heat 값 제한
* Heat가 변경되면 이벤트 발생

### `CoreManager`

* 현재 장착 중인 Core 관리
* Core 교체 처리
* 현재 `CoreData` 제공
* Core가 변경되면 이벤트 발생

### `UIManager`

* `HeatManager`와 `CoreManager` 참조
* Heat·Core 이벤트 구독
* 시스템에서 받은 데이터를 각 Drawer로 전달
* 씬 시작 시 초기 UI 상태 설정

### `HeatDrawer`

* Heat 값을 0~100 범위로 제한
* Heat 값을 이미지의 채움 비율로 변환
* Heat 퍼센트 텍스트 표시

### `CoreDrawer`

* 현재 `CoreData` 수신
* Core 이름 표시
* Core 데이터가 없을 경우 `None` 표시

이렇게 역할을 분리하면서 Heat 계산 방식이 변경되더라도 게이지 표시 코드를 별도로 관리할 수 있고, 반대로 UI 디자인이 변경되더라도 Core 전환 로직을 직접 수정할 필요가 없는 구조를 만들 수 있었다.

작은 규모의 UI였지만, 이후 기능이 늘어날 것을 생각하면 처음부터 책임을 나누어두는 편이 관리하기 쉬울 것이라 판단했다.

## 테스트 UI에서 실제 게임 UI로 확장하기

초기 테스트 단계에서는 `UITestManager`가 임시 Heat 값을 직접 가지고 있었다.

키를 누르면 임시 값이 증가하거나 감소하고, 그 결과가 Heat 게이지에 반영되는 방식이었다.

이 구조는 UI 자체를 빠르게 확인하기에는 편리했지만, 당연히 실제 게임의 상태를 표시하는 구조는 아니었다.

통합 단계에서는 이러한 임시 값 기반의 테스트 구조에서 벗어나, UI가 실제 `HeatManager`와 `CoreManager`의 데이터를 전달받도록 변경했다.

변경 전후를 비교하면 다음과 같다.

### 테스트 단계

**키 입력**
→ **`UITestManager`의 임시 Heat 값 변경**
→ **테스트용 Heat UI 갱신**

### 실제 통합 단계

**공격 또는 Core 전환**
→ **`HeatManager`·`CoreManager`의 실제 상태 변경**
→ **변경 이벤트 발생**
→ **`UIManager`가 이벤트 수신**
→ **`HeatDrawer`·`CoreDrawer` 갱신**

UI 요소는 `Canvas` 프리팹으로 구성한 뒤 플레이어 테스트 씬에 배치했다.

이를 통해 `UITestScene`에서만 사용할 수 있는 임시 UI가 아니라, 이후 다른 씬에서도 재사용할 수 있는 HUD의 기본 구조를 마련했다.

처음에는 키 하나를 눌러 움직이는 테스트용 게이지에 불과했지만, 이 구조를 실제 전투 시스템과 연결하면서 점차 게임에서 사용할 수 있는 HUD로 확장해 나간 셈이다.

## 팀원과의 협업

이번 작업은 UI를 독립적으로 만드는 것만으로 끝나는 작업이 아니었다.

UI가 표시해야 할 정보는 결국 다른 팀원이 구현한 시스템에서 가져와야 했기 때문에, Core와 Heat 시스템의 구조를 이해하고 해당 시스템과 연결하는 과정이 필요했다.

Core와 Heat 시스템을 담당한 팀원이 `CoreManager`와 `HeatManager`를 구현했고, 각 시스템에서 상태가 변경될 때 이벤트가 발생하도록 구성했다. 나는 해당 이벤트를 UI에서 받아 화면에 표시하는 구조를 만들었다.

역할을 정리하면 다음과 같다.

* **시스템 담당:** Core와 Heat의 실제 상태 및 변경 규칙 구현
* **UI 담당:** 상태 변경 이벤트를 받아 HUD에 표시
* **통합 과정:** 테스트 씬에서 만든 UI를 플레이어 테스트 씬과 실제 시스템에 연결

이벤트를 기준으로 시스템과 UI를 연결하면서, UI 코드가 직접 전투 로직을 수정하거나 관리하지 않도록 역할을 나눌 수 있었다.

또한 HP 시스템이 아직 연결 가능한 상태가 아니라는 점을 확인한 뒤, 임시 로직을 추가하여 완성된 것처럼 처리하지 않았다.

현재 준비되어 있는 Heat와 Core부터 먼저 통합하고, HP 시스템이 구현된 이후 남겨둔 부분을 이어서 연결하는 방향으로 작업 범위를 조정했다.

이번 작업을 진행하면서 팀 프로젝트에서는 단순히 내가 필요한 기능을 모두 직접 만들어버리는 것보다, **다른 팀원이 만든 시스템과 역할을 존중하면서 서로의 코드를 연결하는 과정 자체가 중요하다**는 점을 조금씩 느낄 수 있었다.

하지만 최종 디자인을 완성하는 것보다 먼저, **전투 시스템의 데이터가 HUD까지 전달되는 기본적인 흐름을 실제 게임 안에 만들어냈다는 점**에서 의미 있는 첫 단계였다고 생각한다.
