> 「Virtual Developer Transformation――その可能性を試す。」

**『Project VX』**は、AIをゲーム開発の中へ深く組み込み、人間が持つアイデアをどこまで実際のゲームとして形にできるのかを検証する実験プロジェクトである。

ただAIにコードを書かせるだけのプロジェクトではない。

企画を読み、現在の開発状況を把握し、次に必要な作業を判断する。必要であれば作業を細かなTaskへ分解し、実装する。そしてUnity上で実際に動作を確認し、問題があれば原因を調査して修正する。最後に変更内容をGitへ記録し、現在の開発状態を更新したうえで、再び次の作業へ進んでいく。

私が確かめたいのは、こうした一連のゲーム開発サイクルそのものを、AIが継続して担うことができるのかということである。

そして、もしそれが可能になったとき、人間はゲーム開発の中で何を担当するべきなのか。

『Project VX』では、実際にゲームを作りながら、その可能性を一つずつ確かめていく。

---

## 🌙 『Project VX』とは？

近年、生成AIは急速に発展し、プログラミングの分野でもコード生成だけでなく、修正、レビュー、デバッグなど、さまざまな作業を行えるようになった。

しかし、実際にゲームを作ってみれば分かる通り、ゲーム開発は単純に「コードを書く」だけでは成立しない。

一つの機能を実装するだけでも、

* 企画や仕様を理解する
* 既存システムとの依存関係を確認する
* 適切な実装方法を考える
* Unity上で実際に動作させる
* 他の機能を壊していないか確認する
* 問題があれば原因を調査する
* 修正内容を記録する
* 次の作業を判断する

といった、いくつもの工程が必要になる。

さらに開発期間が長くなれば、「今どこまで完成しているのか」「なぜ以前この設計を選んだのか」「この機能は何に依存しているのか」「次に何を実装するべきなのか」といった、**開発状態そのものを維持する能力**も必要になる。

一度のPromptに対して、それらしいコードを生成できるだけでは足りないのである。

Project VXで私が検証したいのは、AIがどれほど大量のコンテンツを生成できるかではない。

**AIが一つの継続したゲーム開発Workflowの中で、実際の開発者に近い形で働き続けることができるのか。**

そこが、このProjectの中心にある問いである。

つまり、Project VXで作っているものはゲームだけではない。

**「AIがゲームを開発するための開発環境」そのものも、Project VXにおける一つの成果物なのである。**

---

## 🚀 「Virtual Developer Transformation」とは？

VXは、**Virtual Developer Transformation**を意味している。

ここで私が重視しているのは、「Automation」ではなく「Transformation」であるという点だ。

Project VXが目指しているのは、人間が今まで行ってきた作業を、そのままAIへ置き換えることではない。

従来の、

**Human Developer**

という開発形態そのものを、

**Human + Virtual Developer**

という形へ変えていくことを試している。

### 🤖 「AIを使う」から「AIを開発者にする」へ

現在でもAIに、

「このコードを書いてほしい」

「このエラーを直してほしい」

「この機能を実装してほしい」

と依頼することは簡単にできる。

私自身も、これまでそうした形でAIを何度も開発へ利用してきた。

しかし、この方法では人間が毎回作業内容を考え、必要な情報を集め、実装範囲を決め、AIへ細かな指示を与える必要がある。

言い換えれば、AI自身が開発を進めているというより、**人間がAIという非常に高性能な開発ツールを操作している状態**に近い。

Project VXでは、そこからさらに一歩先へ進む。

人間がゲームの企画や目的を提示すれば、AI自身が現在の開発状況を確認し、

「次に何をするべきか」

「どこまで実装するべきか」

「作業を始める前に何を確認するべきか」

を判断できる環境を構築する。

人間がすべての実装手順を決めるのではない。

人間は**「何を作りたいのか」**を考え、Virtual Developerは**「それをどう実現するのか」**を考える。

私がProject VXで試しているVirtual Developer Transformationとは、そのような開発形態である。

---

## 🎼 バーチャル開発者「ルミ」

Project VXの中心にいるのが、AIオーケストレーター**「ルミ」**である。

とはいえ、ルミ自身がすべてのコードを書き、すべての作業を直接行うわけではない。

ルミは企画、現在の開発状態、利用できるツール、作業のリスクなどを確認し、その時点で必要な手段を選びながら開発全体を進めていく。

人間の開発チームに例えるのであれば、一人のプログラマーというよりも、**開発状況を把握したうえで必要な担当者やツールへ仕事を振り分けるオーケストレーター**に近い。

### 🎻 AI Orchestration

Project VXでは、一つのAI Modelだけですべてを処理する構成にはしていない。

ルミを中心として、

* 企画情報
* Coding Agent
* 複数のAI Model
* Unity CLI
* Unity MCP
* Git
* Unity Editor

などを接続し、必要に応じて使い分ける。

基本的な構造を簡単に表すと、次のようになる。

**Human**

↓

**Planning / Design Source**

↓

**AI Orchestrator「ルミ」**

↓

**Coding Agent「Codex」**

↓

**Unity CLI & MCP**

↓

**Unity**

↓

**Test / Review / Git**

ルミは「一人ですべてを行うAI」ではない。

必要な作業を適切なAgentやToolへ渡し、その結果を確認し、再び現在の開発状態へ反映していく。

複数のAIとToolを組み合わせ、それら全体を一つのVirtual Developerとして動かす。

Project VXでは、この考え方を**AI Orchestration**として扱っている。

---

## 🪢 AIを制御する「Harnessing」

Project VXを進める中で、予想以上に重要だと感じるようになったものが**Harnessing（ハーネシング）**である。

Projectを始める前であれば、「より高性能なAI Modelを使えば、そのままより優秀な開発者になるのではないか」と考えることもできる。

しかし、実際にAIへ長時間の開発を任せてみると、それだけでは解決できない問題が次々と見えてきた。

例えば、必要以上に内部実装を調べ続けたり、既存の仕様を勝手に変更したり、本来必要のない機能まで追加してしまうことがある。

一つの問題を修正した結果、別の機能を壊すこともある。十分なテストを行わないまま「完了した」と判断することもあれば、Rate LimitやTool Timeoutによって作業が止まったあと、すでに終わっている部分まで最初からやり直そうとすることもあった。

また、長期間の開発では、過去に行った判断や現在のMilestoneを正しく引き継げなければ、それだけで開発全体が不安定になる。

こうした問題は、単純にModelをより高性能なものへ変更しただけでは完全には解決できなかった。

そこでProject VXでは、AIが開発を行うための**ルール、状態管理、検証手順、復旧方法そのもの**を設計している。

それがHarnessingである。

### 🧭 「何をするか」ではなく、「どう働くか」まで決める

Harnessingでは、例えば次のような内容を定義している。

* 作業開始前に確認する情報
* 企画資料と開発状態の優先順位
* 現在のMilestoneを判断する方法
* Codexへ作業を委任する条件
* Unity上での検証方法
* Integration / Regression Testの条件
* Gitの運用方法
* Tool TimeoutやRate Limit発生時の復旧方法
* 再試行する条件
* 作業をPARTIAL / BLOCKEDとして停止する条件
* より高い推論能力を持つModelへ判断を引き上げる条件
* Independent Reviewを行う条件

要するに、**AIへ毎回答えを教えるのではなく、AI自身がより正しい答えへ近づける仕事環境を作る**という考え方である。

そのためProject VXでは、ゲーム本体のCodeだけでなく、Harnessingそのものも継続して開発している。

AIが失敗したときも、単に「AIが間違えた」で終わらせるのではない。

「なぜ現在のHarnessingでは、この失敗を防ぐことができなかったのか」

そこまで遡って確認し、必要であればルールそのものを修正する。

この繰り返しによって、ゲームだけでなくVirtual Developerそのものも改善していく。

---

## 🔀 作業に応じてAIを切り替える「Model Routing」

もう一つ、Project VXで重視しているものが**Model Routing**である。

すべての作業に、最も高性能で最もコストの高いAI Modelを使う必要はない。

単純なファイル確認と、複数のシステムへ影響するArchitecture変更では、当然ながら必要になる推論能力も異なるからだ。

そこでProject VXでは、作業の難易度、曖昧さ、失敗した場合の影響、Regression Riskなどに応じて利用するModelを変更している。

基本的な考え方は、

**「必要十分なModelから始め、本当に必要な場合だけ上位Modelへ引き上げる」**

というものである。

通常の作業は比較的軽いModelへ任せる一方、

* 高リスクな変更
* 複雑なIntegration
* Architectureに関する判断
* 不確実性の高いDebug
* 繰り返し失敗した作業
* 最終検証
* Independent Review

などでは、より高い推論能力を持つModelを利用する。

現在はLuna系・Sol系のModelを中心に、実際の開発結果を見ながらRouting Ruleを調整している。

ここでも重要なのは、「最も強いModelを使い続ければよい」ということではない。

**必要な場所へ、必要な能力を配置すること。**

それもVirtual Developerを現実的に運用するために必要な設計の一つである。

---

## 📚 「設計」と「開発状態」を分離する

長期間AIと開発を続けるうえで、もう一つ問題になったのが情報の管理である。

ゲームに関するすべての情報を、一つの巨大なPromptへ詰め込むことは現実的ではない。

そこでProject VXでは、**Design SourceとDevelopment Stateを分離**して管理している。

ゲームそのものの企画や設計については、Obsidian上の『Project VX Planning』を**Source of Truth**としている。

一方で、

* 現在どのMilestoneにいるのか
* 何が完了したのか
* 次に何をするのか
* 何がまだ検証されていないのか
* どこで作業が中断されたのか

といった、実際の開発状況についてはDevelopment Plan側で管理する。

これによって、

**「ゲームとして何が正しいのか」**

と、

**「そのうち現在どこまで実装されているのか」**

を分けて考えることができる。

一見すると小さな違いだが、開発期間が長くなるほど、この分離は重要になってくる。

---

## 🔄 Project VXの開発Workflow

現在のProject VXでは、おおむね次のような流れで開発を進めている。

**Planning Document**

↓

**Development Plan**

↓

**現在のMilestone / Taskを判断**

↓

**ルミがCodexへ実装を委任**

↓

**Unity上へ実装**

↓

**機能検証**

↓

**Integration / Regression Test**

↓

**必要に応じてIndependent Review**

↓

**Git Commit / Merge**

↓

**Development Planを更新**

↓

**次のMilestoneへ**

こうして並べてみると、一般的なゲーム開発とそこまで大きく違わないようにも見える。

しかし、それはある意味では意図した結果でもある。

Project VXで私が作りたいのは、AIのためだけに存在する特殊なゲーム開発方法ではない。

**人間がこれまで行ってきた実際の開発Workflowへ、AIを一人の開発主体として参加させること。**

そのため、最終的なWorkflowそのものは、むしろ普通のゲーム開発に近い形である方が自然だと考えている。

---

## 🧯 「失敗しないAI」ではなく「失敗から復帰できるAI」

Project VXでは、AIが一度も失敗しないことを前提にはしていない。

実際の開発中にも、Tool Timeout、Rate Limit、実装ミス、認識のずれなど、さまざまな問題が発生した。

特にTest Game 02の開発では、Codexによる作業が途中で停止した際、単純に同じ作業を最初から実行し直すことが必ずしも正しくないと分かった。

すでに一部のCodeが実装されているかもしれない。

Unity側には変更が反映されているかもしれない。

Codex側には、途中まで作業した既存Sessionが残っているかもしれない。

その状態を確認せずに最初からやり直せば、重複した実装や新しい不具合を生む可能性すらある。

そこでHarnessingへ追加した考え方が、**Execution State Persistence and Recovery**である。

作業が中断した場合は、まず現在のProject State、既存Session、Unityの状態を確認する。

そのうえで完了済みの作業と未完了の作業を分離し、必要な部分だけを再開する。

それでも復旧できない場合には、無限に再試行するのではなく、PARTIALまたはBLOCKEDとして現在の状態を残す。

つまりProject VXでは、**「AIを絶対に失敗させないこと」よりも、「失敗しても開発を壊さずに戻ってこられること」**を重視している。

実際の開発者がそうであるように、Virtual Developerも失敗する。

だからこそ、失敗したあとにどう戻るかまで設計する必要があるのである。

---

## 👤 人間は何をするのか？

では、AIがこれほど多くの作業を担当するようになれば、人間は必要なくなるのだろうか。

少なくとも、Project VXではそのようには考えていない。

AIは大量の情報を読み、Codeを書き、状態を比較し、何度もTestを繰り返すことを得意としている。決められた基準に沿って問題を探したり、定型的な作業を何度も実行したりすることも得意だ。

一方で、

「この操作は気持ちいいのか」

「このCameraは見やすいのか」

「この演出は格好いいのか」

「このゲームを遊びたいと思えるのか」

「そもそも、私は何を作りたいのか」

という問いには、唯一の正解が存在しない。

例えばProject VXのTestでは、AIによる実装が技術的には正常であっても、実際に私がプレイした結果、Cameraの見え方、移動感覚、戦闘のテンポ、Stageの分かりやすさなどを改めて判断する必要があった。

ここは現在のAIへそのまま任せるよりも、人間が直接体験した方がはるかに分かりやすい部分である。

そのためProject VXでは、人間を開発Workflowの外へ追い出すのではなく、**Human in the Loop**として重要な判断地点へ配置している。

人間が目的を決める。

AIが実装する。

人間が実際に体験し、評価する。

必要であれば方向を修正する。

そしてAIが再びそれを実装する。

人間とAIのどちらか片方だけが開発するのではなく、**異なる強みを持つ二つの開発主体として協働すること。**

それもVirtual Developer Transformationにおける重要なテーマの一つである。

---

## 🧪 『Project VX』の実験方法

Project VXでは、最初から大規模なゲーム制作へ挑戦するのではなく、複数の小規模な**Test Game**を制作しながら、段階的に開発環境を検証している。

それぞれのTest Gameで確認するのは、単に「ゲームを完成させられたか」だけではない。

**そのゲームを作る過程のうち、どの範囲までをAIへ任せることができたのか。**

そして、どこで人間の介入が必要になり、どの失敗をHarnessingによって防ぐことができたのか。

ゲームそのものと同時に、開発Workflowについても評価していく。

---

### 🧪 Test Game 01 — 基本Pipelineの検証

最初のTest Gameでは、

**ルミ → Codex → Unity**

という基本的なAIゲーム開発Pipelineが成立するかを確認した。

この段階で重要だったのは、複雑なゲームを作ることではない。

AIが企画を受け取り、Coding Agentへ実装を依頼し、実際のUnity Projectへ変更を加え、それをゲームとして動作させる。

まずは、この最小限の流れが成立するかを確認した。

Test Game 01によって、AIを利用して実際のUnity Gameを制作するPipelineそのものは成立することを確認できた。

しかし同時に、一度の作業ではなく、複数日にわたって継続的にゲームを開発するのであれば、より明確なPlanning、状態管理、検証、復旧、そしてGit運用が必要であることも見えてきた。

そこでTest Game 02では、検証する範囲を大きく広げることにした。

---

### 📡 Test Game 02 — LAST SIGNAL

**『LAST SIGNAL』**は、約10〜15分でプレイできる2.5Dアクション・探索・パズルゲームである。

Test Game 01が「AIを利用してゲームを作るPipelineそのものが成立するか」を確認するTestだったのに対し、Test Game 02では、

**「複数のゲームシステムを持つ一つのゲームを、Planningに基づいて最初から最後まで継続して開発できるのか」**

を検証している。

実装対象には、

* Player / Camera
* 3段通常攻撃
* Dodge
* Skill
* Damage System
* Enemy AI
* Generator
* Interaction
* Puzzle
* Checkpoint
* Transmission
* Boss
* UI
* Game State
* Game Flow

など、小規模なゲームを一本成立させるために必要となる複数のSystemが含まれている。

これらを一度に実装するのではなく、M0〜M8までのMilestoneへ分割し、順番に開発している。

| Milestone                    | 内容                                                 |     状態     |
| :--------------------------- | :------------------------------------------------- | :--------: |
| **M0 — Project Bootstrap**   | Projectの基盤構築                                       |   ✅ Done   |
| **M1 — Player**              | Player移動・Cameraなどの基礎                               |   ✅ Done   |
| **M2 — Combat**              | 攻撃・Damage・Skillなどの戦闘System                         |   ✅ Done   |
| **M3 — Enemy**               | Enemy AI・攻撃・Projectileなど                           |   ✅ Done   |
| **M4 — Level / Interaction** | Stage・Generator・Interactionなど                      |   ✅ Done   |
| **M5 — Game State**          | Checkpointなどゲーム状態の管理                               |   ✅ Done   |
| **M6 — Boss**                | Boss戦および関連System                                   |   ✅ Done   |
| **M7 — Game Flow**           | Main Menu・Pause・Game Over・Game Clear・Transmission  |   🔄 Next  |
| **M8 — Polish / QA**         | VFX・SFX・Camera Feedback・Balance・Bug Fix・Regression | 📅 Planned |

M8まで完了した時点で、**Critical Bugがなく、ゲームを最初から最後まで通してプレイできること**をTest Game 02の最終的な完了条件としている。

---

## 🔍 「実装した」だけでは完了しない

Project VXでは、Codeを書き終えただけでMilestoneを完了したとは扱わない。

特に重要な機能については、Unity上で実際に動かしたうえで確認する。

例えばEnemyについても、「攻撃するCodeが存在する」「PlayerがDamageを受ける」というだけでは不十分である。

実際のゲームプレイ中に、

* 攻撃範囲は正しいか
* 壁越しに攻撃していないか
* Projectileが環境を無視していないか
* 一回の攻撃が同じ対象へ重複Hitしていないか
* 今回の変更によって既存機能が壊れていないか

といった部分まで確認する必要がある。

そのためTest Game 02では、機能単体の確認だけでなく、**Integration Test**と**Regression Test**を重視している。

さらに、変更のRiskが高い場合やMilestoneの節目では、実装を行った判断系統とは別に**Independent Review**を行う。

実装した側が、自分の判断ミスをそのまま正しいものとして扱ってしまう可能性を減らすためである。

AIだから特別というよりも、このあたりは人間同士のCode Reviewとそれほど変わらないのかもしれない。

---

## 🌿 必要なものだけを作る

AIによる実装を見ていると、必要以上に一般化されたSystemや、「将来使うかもしれない機能」を先に作ろうとすることがある。

しかし、Project VXはAIがどれほど大量のCodeを書けるかを競うProjectではない。

そのため、現在は次の考え方を基本としている。

* 現在のMilestoneを完成させるために必要な機能を優先する
* 次のMilestoneを先行実装しない
* 再利用性は確保するが、必要以上に抽象化しない

Virtual Developerに必要なのは、頼めば何でも作ってくれる能力だけではない。

**今、本当に必要なものが何なのかを判断し、それだけを作る能力も必要なのである。**

---

## 🌱 Project VXで作りたいもの

Project VXの最終的な目的は、Test Gameを大量に作ることではない。

Test Gameを通して、

* Planning
* Orchestration
* Harnessing
* Model Routing
* Implementation
* Testing
* Recovery
* Review
* Git Workflow

といった開発Pipelineを一つずつ実際に検証し、AIがより安定してゲーム開発へ参加できる環境を作ることが目的である。

そして十分な結果が得られれば、Project VXで構築したVirtual Developerを、VX専用の実験環境から、**より一般的なゲーム開発でも利用できる開発System**へ発展させたいと考えている。

つまり、最終的に残したいものは一つのゲームだけではない。

ゲームそのもの。

## 🗺️ 『Project VX』の開発計画

Project VXでは、複数のTest Gameを通して段階的に検証範囲を広げていく予定である。

| Phase                          | 主な検証内容                      |       状態       |
| :----------------------------- | :-------------------------- | :------------: |
| **Test Game 01**               | ルミ–Codex–Unity基本Pipelineの検証 |     ✅ Done     |
| **Test Game 02 — LAST SIGNAL** | Planningを含む統合開発Workflowの検証  | 🔄 In Progress |
| **Test Game 03**               | より実践的な開発環境・Harnessingの検証    |   📅 Planned   |
| **Project VX**                 | 検証結果を利用した本格的なゲーム制作          |   📅 Planned   |

各Testで発生した失敗や問題は、単に「今回は失敗した」として次のTestへ持ち越すのではなく、可能な限りHarnessingやWorkflowへ反映する。

そして次のTestでは、同じ問題が再び起こるのかを確認する。

Testを重ねるたびに完成するゲームだけでなく、**Virtual Developerそのものも少しずつ成長していく。**

そのような構造を目指している。

## ✨ 『Project VX』が試す可能性

AIは、ゲーム開発者になれるのだろうか。

現時点では、私にもまだ答えは分からない。

おそらく、最後まで検証したとしても、「AIだけですべてできる」という単純な結論にはならないと思う。

人間にしか判断しにくいことがある。

一方で、AIの方が圧倒的に得意なこともある。

だから重要なのは、どちらか一方を選ぶことではない。

人間がアイデアを生み出す。

Virtual Developerが、それを実装へ変換する。

人間が実際に結果を体験し、判断する。

AIがその判断を次の実装へ反映する。

失敗すれば原因を調べる。

Harnessingを修正する。

そして、もう一度試す。

そのサイクルを何度も繰り返した先で、

**一人では実現できなかったものを、どこまで形にすることができるのか。**

Project VXは、その可能性を実際のゲーム開発を通して確かめるためのProjectである。

このページもまた、Project VXの進行とともに少しずつ更新していくつもりだ。
