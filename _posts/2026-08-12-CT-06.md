5주차에는 이렇게 만들어둔 Pause 화면을 **실제로 조작할 수 있는 메뉴에 가까운 형태로 발전시키는 작업**을 진행했다.

따라서 이번 주에는 Pause 메뉴에서 실제로 사용할 수 있는 **Resume와 볼륨 설정을 우선 구현하고**, Core 2·3에도 대응할 수 있도록 UI 에셋과 참조 구조를 확장하는 데 집중했다.

## Resume 버튼 실제 연결

4주차에는 `Button_Resume` 오브젝트와 `PauseManager`의 재개 로직이 각각 존재했지만, 실제 버튼의 `OnClick` 이벤트는 비어 있었다.

5주차에는 Resume 버튼을 `PauseManager.TogglePause()`에 연결했다.

```csharp
public void TogglePause()
{
    if (isPaused)
        Resume();
    else
        Pause();
}
```

Pause 상태에서 Resume 버튼을 누르면 `isPaused`가 `true`이므로 `Resume()`이 호출된다.

```csharp
private void Resume()
{
    if (!isPaused)
        return;

    isPaused = false;
    Time.timeScale = 1f;

    playerController.SetInputEnabled(true);
    pausePanel.SetActive(false);

    Cursor.visible = false;
    playerInput.SwitchCurrentActionMap("Player");
}
```

Resume 버튼을 누르면 다음 상태가 원래대로 복구된다.

* `Time.timeScale`을 `1`로 복구
* 플레이어 입력 활성화
* Pause Panel 비활성화
* 마우스 커서 숨김
* Input Action Map을 `UI`에서 `Player`로 복귀

4주차에는 ESC를 다시 눌러야만 Pause 상태에서 빠져나올 수 있었다면, 5주차부터는 **화면의 Resume 버튼을 직접 클릭해 게임으로 돌아갈 수 있게 된 것**이다.

**[캡처 1 삽입 — Pause 화면의 Resume 버튼]**

> 4주차에 배치만 해두었던 Resume 버튼을 `PauseManager`와 연결했다. 버튼을 누르면 게임 시간과 플레이어 입력이 복구되고 Pause 화면이 닫힌다.

## UI 버튼 동작을 별도 클래스로 분리

Pause 화면의 버튼 동작을 관리하기 위한 `UIButtonsActions`도 추가했다.

```csharp
public void ResumeGame()
{
    PauseManager.Instance?.TogglePause();
}

public void OnPause(
    InputAction.CallbackContext context
)
{
    if (!context.performed)
        return;

    PauseManager.Instance?.TogglePause();
}

public void TogglePause()
{
    PauseManager.Instance?.TogglePause();
}
```

이 클래스는 Resume 버튼이나 Input Action 등 여러 UI 요소에서 `PauseManager`의 상태 전환을 호출할 수 있는 중간 진입점 역할을 한다.

다만 5주차 당시 테스트 씬에 저장된 Resume 버튼의 실제 `OnClick` 연결은 `UIButtonsActions.ResumeGame()`이 아니라 `PauseManager.TogglePause()`를 직접 호출하는 형태였다.

따라서 현 단계에서는 `PauseManager`가 실제 Pause 상태를 관리하고, `UIButtonsActions`는 이후 버튼 동작을 분리하기 위해 마련한 **보조적인 UI 진입 계층**에 가까웠다.

## Pause 메뉴 오브젝트 구조 정리

Resume 버튼을 연결하는 과정에서 Pause 관련 오브젝트 구조 역시 함께 정리했다.

Pause 화면에는 다음과 같은 오브젝트들이 존재했다.

* `Pause Manager`
* `Pause Panel`
* `Pause Shader`
* `Pause Frame`
* `Pause Menu Buttons`
* `Button_Resume`
* 테스트용 버튼
* 마우스 반응형 배경 제어 오브젝트

기존에는 버튼과 Panel, `PauseManager`의 참조가 다소 분산되어 있어 어떤 오브젝트가 실제 상태를 관리하는지 한눈에 파악하기 어려운 부분이 있었다.

그래서 다음과 같이 책임을 기준으로 구조를 정리했다.

* `PauseManager`: 실제 Pause·Resume 상태 관리
* `Pause Panel`: Pause 화면 전체 표시
* `Pause Shader`: 동적 배경 표시
* `Pause Menu Buttons`: Resume 및 이후 추가할 메뉴 버튼 그룹
* `PauseMouseController`: 마우스 위치를 Shader 값으로 변환
* `PauseMenuMotion`: 마우스 위치에 따라 메뉴 위치와 크기 변경

이 과정에서 Resume 버튼이 동작하지 않던 참조 문제 역시 함께 수정했다.

단순히 기능 하나를 추가한 것이 아니라, 앞으로 Setting이나 Exit 버튼이 추가되더라도 기존 구조 안에 자연스럽게 넣을 수 있도록 **Pause UI 내부의 역할을 다시 정리한 셈**이다.

## 마우스 위치에 따라 Pause 메뉴 움직이기

4주차에는 마우스의 X좌표를 Pause 배경 Shader의 `_Progress` 값과 연결했다.

5주차에는 이 값을 배경에만 사용하는 것이 아니라, 실제 메뉴 오브젝트의 움직임에도 활용하도록 확장했다.

먼저 `PauseMouseController`에서 현재 값을 외부에서도 읽을 수 있도록 공개했다.

```csharp
public float Progress => progress;
public float Center => center;
public float MoveRange => moveRange;
```

`PauseMenuMotion`은 이 값을 받아 메뉴의 위치와 크기를 변경한다.

```csharp
float progress = controller.Progress;

float center = controller.Center;
float range = controller.MoveRange;

float t = Mathf.InverseLerp(
    center - range,
    center + range,
    progress
);
```

현재 Progress가 설정된 범위 안에서 어느 정도 위치에 있는지를 `0~1` 사이의 값으로 변환한다.

이 값을 이용해 메뉴를 좌우 또는 대각선 방향으로 이동시켰다.

```csharp
Vector2 dir = new Vector2(
    Mathf.Cos(moveAngle * Mathf.Deg2Rad),
    Mathf.Sin(moveAngle * Mathf.Deg2Rad)
);

float move = Mathf.Lerp(
    -moveDistance,
    moveDistance,
    t
);

rect.anchoredPosition =
    defaultPos + dir * move;
```

마우스 위치에 따라 메뉴의 크기 역시 함께 변화하도록 했다.

```csharp
float scale = Mathf.Lerp(
    minScale,
    maxScale,
    t
);

rect.localScale =
    defaultScale * scale;
```

이제 Pause 화면에서 마우스를 좌우로 움직이면 배경 Shader만 변화하는 것이 아니라, 메뉴 오브젝트 역시 미세하게 이동하고 확대·축소된다.

4주차에는 마우스가 **배경에 반응**했다면, 5주차에는 메뉴까지 같은 값을 공유하면서 화면 전체가 하나의 인터페이스처럼 움직이도록 확장한 것이다.

**[캡처 2 삽입 — 마우스 좌·중앙·우 위치에 따른 Pause 메뉴 변화]**

> `PauseMouseController`의 Progress 값을 메뉴에도 공유했다. 마우스 위치에 따라 Pause 배경뿐 아니라 메뉴의 위치와 크기도 함께 변화한다.

이 기능은 정적인 이미지보다는 짧은 GIF로 보여주는 편이 실제 움직임을 전달하기에 더 적합할 것 같다.

## Master·BGM·SFX 볼륨 구조

Pause 메뉴에서 실제로 사용할 수 있는 기능으로, 게임의 사운드를 조절하는 볼륨 컨트롤도 추가했다.

볼륨은 다음 세 그룹으로 구분했다.

* Master
* BGM
* SFX

`MainAudioMixer`에서는 Master 그룹을 최상위에 두고, BGM과 SFX를 그 하위 그룹으로 구성했다.

구조는 다음과 같다.

**MainAudioMixer**
└─ **Master**
　├─ **BGM**
　└─ **SFX**

각 그룹의 볼륨을 코드에서 변경할 수 있도록 다음 파라미터를 외부에 노출했다.

* `MasterVolume`
* `BGMVolume`
* `SFXVolume`

이를 통해 전체 음량, 배경 음악, 효과음을 각각 독립적으로 조절할 수 있도록 했다.

또한 BGM과 SFX는 Master 아래에 있기 때문에, Master 볼륨을 조절하면 두 그룹의 전체적인 음량도 함께 영향을 받는다.

**[캡처 3 삽입 — MainAudioMixer의 Master·BGM·SFX 구조]**

> `MainAudioMixer`를 Master, BGM, SFX 그룹으로 나누고 각 그룹의 Volume 파라미터를 외부에 노출했다.

## 세 개의 볼륨 Slider 연결

`VolumeController`에는 Master, BGM, SFX를 각각 조절할 세 개의 Slider를 연결했다.

```csharp
[Header("Audio Mixer")]
[SerializeField]
private AudioMixer audioMixer;

[Header("Volume Sliders")]
[SerializeField]
private Slider masterVolumeSlider;

[SerializeField]
private Slider bgmVolumeSlider;

[SerializeField]
private Slider sfxVolumeSlider;
```

씬에는 다음 Slider를 배치했다.

* `MasterVolumeSlider`
* `BGM Slider`
* `SFX Slider`

게임이 시작되면 각 Slider의 값 변경 이벤트에 처리 메서드를 등록했다.

```csharp
private void Start()
{
    masterVolumeSlider.onValueChanged
        .AddListener(SetMasterVolume);

    bgmVolumeSlider.onValueChanged
        .AddListener(SetBGMVolume);

    sfxVolumeSlider.onValueChanged
        .AddListener(SetSFXVolume);
}
```

각 Slider는 `MainAudioMixer`에 노출해둔 해당 파라미터와 연결된다.

```csharp
private void SetMasterVolume(float value)
{
    SetVolume("MasterVolume", value);
}

private void SetBGMVolume(float value)
{
    SetVolume("BGMVolume", value);
}

private void SetSFXVolume(float value)
{
    SetVolume("SFXVolume", value);
}
```

하나의 공통 볼륨 변환 함수를 사용하되, 변경할 Mixer 파라미터만 다르게 전달하는 구조로 만들었다.

**[캡처 4 삽입 — Pause 화면의 Master·BGM·SFX Slider]**

> Pause 화면에서 전체 음량과 BGM, SFX를 각각 조절할 수 있도록 세 개의 Slider를 추가했다.

## Slider 값을 데시벨로 변환하기

Unity UI Slider는 일반적으로 `0~1` 사이의 값을 사용하지만, AudioMixer의 Volume 파라미터는 데시벨 단위로 처리된다.

따라서 Slider 값을 그대로 AudioMixer에 전달하지 않고, 로그 함수를 이용해 데시벨로 변환했다.

```csharp
private void SetVolume(
    string parameterName,
    float value
)
{
    float volume =
        value <= 0.0001f
            ? -80f
            : Mathf.Log10(value) * 20f;

    audioMixer.SetFloat(
        parameterName,
        volume
    );
}
```

Slider 값이 0에 가까울 때에는 로그 계산을 수행하지 않고 `-80dB`를 전달해 사실상 음소거 상태가 되도록 했다.

그 외의 값에는 다음 변환식을 사용했다.

**데시벨 = log10(Slider 값) × 20**

대략적으로 다음과 같이 변환된다.

* Slider `1.0` → 약 `0dB`
* Slider `0.5` → 약 `-6dB`
* Slider `0.1` → 약 `-20dB`
* Slider `0` → `-80dB`

Slider 값을 단순히 선형적인 데시벨 값과 대응시키는 것보다, 사람이 실제로 느끼는 음량 변화에 조금 더 가까운 조절이 가능하도록 로그 변환을 사용했다.

## AudioSource의 Mixer 연결 조건

볼륨 Slider가 실제 게임의 사운드에 영향을 주려면, 각 `AudioSource`의 Output이 `MainAudioMixer` 계열의 그룹에 연결되어 있어야 한다.

예를 들면 다음과 같다.

* 배경 음악 `AudioSource` → BGM 그룹
* 공격·피격·Skill 효과음 → SFX 그룹
* 아직 세부 분류하지 않은 사운드 → Master 그룹

BGM과 SFX는 Master의 하위 그룹이므로, 각각의 그룹에 연결된 `AudioSource` 역시 Master Slider의 영향을 함께 받는다.

반대로 `AudioSource`의 Output이 `None`으로 남아 있다면 `MainAudioMixer`를 거치지 않기 때문에, Slider를 움직여도 실제 사운드에는 변화가 없다.

당시 팀에도 다음 사항을 공유했다.

> 현재 게임에서 재생되는 AudioSource가 MainAudioMixer의 Master로 연결되어 있어야 합니다.

다만 실제 구조에서는 모든 사운드를 Master에만 연결하기보다, 사운드의 종류에 맞게 BGM과 SFX로 구분해야 각 Slider가 의도한 대로 작동한다.

**[캡처 5 삽입 — AudioSource의 Output을 BGM 또는 SFX에 연결한 Inspector]**

> `VolumeController`가 정상적으로 동작하려면 게임에서 사용하는 `AudioSource`의 Output을 `MainAudioMixer`의 BGM 또는 SFX 그룹에 연결해야 한다.

private void OnEnable()

## Heat UI 위치 변경과 Shader 수정

Pause 화면과 Core UI의 디자인이 변경되면서 Heat UI의 위치와 형태 역시 함께 조정할 필요가 있었다.

기존 Heat Shader는 이전 프레임의 Fill 방향과 형태를 기준으로 만들어져 있었다.

새로운 Heat UI에서는 디자인의 방향이 바뀌었기 때문에, 기존 Shader Graph를 `HeatBarShader_Old`로 따로 보관하고 새로운 `HeatBarShaderGraph`를 추가했다.

Heat 값의 진행 방향 역시 새로운 디자인에 맞게 반대로 계산했다.

```csharp
public void SetHeat(
    float current,
    bool isHighHeat
)
{
    current = Mathf.Clamp(
        current,
        0f,
        100f
    );

    current = 100f - current;

    if (materialInstance != null)
    {
        materialInstance.SetFloat(
            "_Fill",
            current / 100f
        );
    }

    if (!isOverHeat)
    {
        heatFill.color =
            isHighHeat
                ? warningColor
                : normalColor;
    }

    if (heatText != null)
    {
        heatText.text =
            $"{100f - current:0}%";
    }
}
```

Shader에는 반전된 Fill 값을 전달하지만, 텍스트에는 실제 Heat 수치가 그대로 표시되도록 다시 계산했다.

예를 들어 실제 Heat가 30이라면 다음과 같이 처리된다.

* 실제 Heat: `30`
* Shader Fill 계산용 값: `70`
* 표시 텍스트: `30%`

이는 새로운 Heat 프레임의 시각적인 진행 방향에 맞추기 위한 구현이었다.

플레이어에게 전달되는 의미는 그대로 유지하면서, **Shader 내부에서 사용하는 값만 디자인에 맞게 반전**한 셈이다.

**[캡처 8 삽입 — Heat UI 개편 전후 비교]**

> Heat UI의 위치와 프레임 형태가 변경되면서 Shader Graph와 Fill 계산 방향도 함께 수정했다.

## Pause 중 Core 전환 문제 재확인

4주차에 발견했던 Pause 중 Core 전환 문제는 5주차에도 그대로 남아 있었다.

`PauseManager`에서는 외부에서 현재 Pause 상태를 확인할 수 있도록 다음 속성을 제공하고 있었다.

```csharp
public bool IsPaused => isPaused;
```

하지만 `CoreManager`는 이 값을 확인하지 않고, 기존 Input API를 통해 숫자 키를 직접 처리하고 있었다.

```csharp
if (Input.GetKeyDown(slot.SelectKey))
{
    SetCurrentCore(i);
}
```

따라서 다음과 같은 Pause 처리만으로는 Core 전환을 차단할 수 없었다.

* `Time.timeScale = 0`
* `PlayerController` 입력 비활성화
* Input Action Map을 `UI`로 전환

당시 기록에는 다음과 같이 수정 방향을 공유했다.

> 여전히 Pause 상태에서 Core 전환이 가능합니다. `public bool IsPaused => isPaused;` 코드가 있으니, 이 부분을 이용하여 Pause일 때 Core 변경을 막는 코드를 추가해 주시면 감사하겠습니다.

이 문제는 Pause 화면 자체보다는 `CoreManager`의 입력 처리 방식에 가까운 문제였다.

따라서 다른 팀원이 담당한 Core 시스템을 직접 수정하는 대신, **이미 제공하고 있는 Pause 상태 값과 수정 방향을 팀에 공유하는 방식**으로 대응했다.

5주차에도 해당 문제는 해결 완료 항목으로 처리하지 않았다.

`SkillRefManager` 역시 Chain·Gun Core를 참조할 수 있도록 구조를 늘렸지만, 아직 실제 Skill 이벤트와의 연결은 테스트하지 못했다. 따라서 참조를 추가했다는 것과 실제 기능이 동작한다는 것을 구분해 기록했다.

Heat UI 역시 새 위치와 형태에 맞춰 Shader Graph와 Fill 방향을 수정했다.

같은 구조를 HP에도 적용할 계획을 세웠지만, HP UI 통일과 상태창·인벤토리는 이후 작업으로 남겼다.

그리고 4주차에 발견한 Pause 중 Core 전환 문제도 여전히 남아 있었다.

다만 이번에는 `PauseManager.IsPaused`라는 명확한 상태 값을 사용할 수 있었기 때문에, Core 시스템에서 해당 값을 확인해 입력을 막는 방향을 팀에 공유했다.

이번 주에도 Pause 화면의 모든 기능을 완성한 것은 아니다.

하지만 4주차에 만든 것은 어디까지나 **게임을 멈추고 화면을 띄우는 기반**이었다면, 5주차에는 Resume와 볼륨 조절처럼 플레이어가 실제로 사용할 수 있는 기능이 들어가기 시작했다.

조금씩이지만, 단순한 Pause 화면이 하나의 메뉴로 변해가고 있었다.
